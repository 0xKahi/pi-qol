# assets/

## Responsibility

The `assets/` directory holds published, generated artifacts that support the `pi-qol` extension. The primary artifact is `config.schema.json`, a JSON Schema (draft-07) generated by `scripts/build-schema.ts` from the canonical Zod config schema in `src/schemas/config.schema.ts`. It defines, documents, and validates the user-facing configuration: available features, default values, accepted value ranges, required fields, and enum constraints so that editors, IDEs, and the extension can load and validate `pi-qol` configuration safely.

## Design Patterns

- **Schema-driven configuration**: User settings are governed by a single JSON Schema generated from the canonical Zod source, ensuring defaults, types, and constraints live in one authoritative location and stay synchronized with runtime validation.
- **Feature-flagged modules**: Each top-level feature (`auto_session_name`, `model_select`, `custom_footer`) is wrapped in an `enabled` boolean, allowing independent activation and deactivation.
- **Nested option objects**: Features group related settings into sub-objects (`model`, `favourite`, `groups`, `hide_tabs`, `provider_filter`, `colors`, `icons`, `display`) to keep the configuration hierarchical and self-documenting.
- **Enum constraints for UX modes**: Discrete choices such as `reasoning` levels (`off`/`minimal`/`low`/`medium`/`high`/`xhigh`) and `layout` modes (`inline`/`overlay`) use JSON Schema `enum` values to prevent invalid configuration.
- **Hex color validation**: `custom_footer` color properties use a `^#[0-9a-fA-F]{6}$` pattern to ensure values are valid six-digit hex colors.

## Data & Control Flow

1. The canonical configuration shape is defined in `src/schemas/config.schema.ts` and validated at runtime with Zod.
2. `scripts/build-schema.ts` invokes `createConfigJsonSchema()` to convert the Zod schema into `assets/config.schema.json` via `z.toJSONSchema(..., { target: 'draft-7' })`.
3. The extension reads the user's configuration (e.g., an editor settings file or `pi-qol.json`).
4. The configuration is validated against `assets/config.schema.json`.
5. Based on each feature's `enabled` flag, individual feature modules are initialized.
6. Feature modules read their respective nested configuration objects (`model.*`, `favourite[]`, `favourite_label`, `groups`, `hide_tabs.*`, `provider_filter`, `colors.*`, `icons.*`, `display.*`) to drive behavior.
7. Optional settings fall back to the schema-defined `default` values when absent.

## Integration Points

- **Extension host / editor settings**: The schema is referenced by editor configurations (via the `$schema` URL or a local path) to provide autocomplete, validation, and tooltips.
- **Feature modules in `src/`**: Source code parses the validated configuration and maps each top-level property to a corresponding feature implementation.
- **Zod schema source**: `src/schemas/config.schema.ts` is the canonical source of truth; the generated schema must be regenerated with `bun run buildSchema` after any schema change.
- **NPM package artifact**: `assets/config.schema.json` is included in the published package payload so consumers can reference it locally or remotely.
- **Default value provider**: The schema's `default` fields act as the canonical source of truth for fallback values across the extension.
